# Stage 1 verification and remaining release gates

Work started September 12 and final checks continued September 13, 2026, on local development branch `codex/reliability-foundation`. No public deployment, paid service, invitation, database migration or real-user task write was performed.

## Changes in this stage

1. Added a reproducible dependency lockfile, a test runner and CI checks. Fixed the obsolete `next lint` command: `npm run lint` currently means TypeScript checking, **not** an ESLint/style audit. Updated Next.js, PostCSS, Sharp and vulnerable compatible transitive dependencies. Updated mobile CI to Node 22 and Android Java 21.
2. Reused a single Supabase client; isolated query caches by account; surfaced failed mutations. Removed authenticated API data from service-worker caching and stopped development bundles getting stuck in that cache. Existing cached Todoer data is cleaned on service-worker activation; this is not a persistent offline task database.
3. Replaced unsafe recurring completion/Undo behavior with conditional completion, version checks, a stable next-task retry ID and explicit partial-failure handling. Corrected local calendar handling and weekday recurrence. No title-based deletion remains in recurring Undo; recurring Undo is intentionally unavailable pending a database transaction.
4. Added personal local reminder preferences, a finite native notification planner, cancellation/reconciliation, quiet hours, snooze, focus suppression, permission status and a phone probe. Local task writes cancel old alerts before updating. Dirty tasks remain suppressed until a fresh database response resolves the mutation. Native shared-list scheduling is not enabled.
5. Recovered focus sessions from stored deadlines and counted completion once. Capture now uses an editable preview, asks for AM/PM when consequential, and keeps drafts on save failure. No model API is used.
6. Fixed project/label URLs for static export, mobile sidebar visibility, accessible task checkboxes, and mobile task-detail layout. Task details now expose Done, Snooze and Reschedule near the top. Main navigation redesign and Daily migration remain later stages.

## Release blockers, in order

1. **Target phone validation.** No Android SDK/Java toolchain or connected phone was available here, and there is no locally verified iOS build. Confirm which phones the household uses and test the actual native binary.
2. **Correct database access and schema.** Read-only schema/policy checks timed out and the configured project lookup returned not found. Export real schema, migrations and access rules before proposing changes. Test owner, partner and outsider accounts; a client filter is not a security rule.
3. **Atomic shared completion and durable retries.** Current recurring completion still uses two writes. If completion succeeds and next-task insertion cannot be confirmed, the UI offers “Retry next task” using the same ID. Closing the page loses that retry payload. A killed process or offline retry can still leave a gap. Stable operation IDs, occurrence links, unique constraints and a database transaction must replace this before release. General create retries also need durable operation IDs to resolve an ambiguous network response without duplicate tasks.
4. **Offline and remote cancellation.** There is no durable task outbox. Completion needs a successful server write; a failed write must not look saved. Device-local snooze can work offline. An offline device cannot know about remote completion. Shared background reminders remain disabled until the release contract and server delivery implementation are tested.
5. **Daily history migration.** The existing Habits screen has not been converted to the single occurrence system. Missed-day, pause, travel and DST policies in the audit are proposed requirements, not passing implementation tests.
6. **Native and release hardening.** Native focus-end alerts, application update behavior, screen-reader/focus-trap coverage, large text, notification quotas with many tasks, account removal on shared devices, production email configuration and store signing remain unverified. Resolve the development asset-tool advisories before using that generator on untrusted input or certifying the build toolchain.

Reminder consent is currently stored per account **on this device**, not synchronized. Clearing browser storage, reinstalling, or moving phones loses those local preferences and focus state. Database tasks remain server records. No automatic migration turns old global nag flags into a partner's consent.

One-time alerts have an unavoidable evidence gap: if permission revocation is first observed after the due time and the OS no longer exposes pending/delivered history, issuance does not prove delivery. This stage retains that alert as consumed to avoid duplicate alerts; it does not automatically replay an uncertain one-time reminder. The overdue task remains visible. Confirmed cancellations before delivery release ownership and can be scheduled again.

Recurring rules are deliberately limited to the formats the existing UI supports; unsupported imported RRULE features need explicit rejection rather than silent interpretation. A plain monthly repeat currently clamps a short month and can drift from an original 31st-day anchor unless the rule explicitly carries that day. Preserve that limitation in the next recurrence/data review; this stage does not certify arbitrary calendar recurrence or the proposed Daily travel policy.

## Phone test: first practical experiment

Install a development build on the actual phone. Open Settings → My reminders → Enable device notifications, then Start background test. It requests alerts in 1, 11 and 21 minutes. Lock the phone and write down the actual arrival time of each alert. Cancel test removes its pending and delivered notifications. This probe is separate from tasks and explicitly bypasses quiet hours; do not run it alongside timed task tests unless testing quota contention.

Record phone model, OS version, build/commit, timezone, permission state, exact-alarm setting, battery restrictions, requested time, actual time and action taken. Repeat with ordinary personal tasks; the probe alone does not verify task cancellation. A force-stopped app and one merely removed from Recents are different test cases.

| Scenario | Expected supported behavior | Status |
| --- | --- | --- |
| Visible app; one timed persistent task; quiet hours off | Roughly one-minute foreground reminders, Done/Snooze/Reschedule available; no accumulated burst after reopening. | Phone: not run |
| Locked/background; notifications/exact alarms allowed | Finite queued Inbox alerts, at least ten-minute requested repeat interval. Measure lateness; no promise of indefinite or exact delivery. | Not run |
| Two or more overdue tasks under Doze | Measure app-wide Android alarm throttling. Ten minutes per task does not avoid the nine-minute per-app idle quota. No release timing claim until measured. | Not run |
| Airplane mode after scheduling | Existing local Inbox alerts can be requested without network. Snooze remains personal. Failed completion remains visibly failed and refresh restores authoritative state when online. | Not run |
| Process killed / Recents swipe | Test separately from force-stop; verify queued delivery and action recovery. | Not run |
| Explicit OS force-stop | Do not promise delivery. Reopening must refetch and replan without duplicating a consumed one-time alert. | Not run |
| Reboot | Check which schedules survive/reinstall and whether permission remains. No guarantee made from plugin registration alone. | Not run |
| Permission denied/revoked, exact alarms off, battery saver, Android Private Space | UI reports restriction; no false “reliable reminder” state; re-enabling permits replanning. Measure lateness or non-delivery. | Not run |
| Complete, delete, move due time, disable persistence | Pending and delivered obsolete alerts disappear; wait past old due times. Include a task due within seconds of the action. | Logic tests passed; phone not run |
| One-time alert delivered in background, then reopen | No second in-app or native one-time alert for the same logical reminder. | Regression tests; phone not run |
| Snooze and quiet hours crossing midnight | No alerts during quiet period/snooze and no backlog afterward. Edit quiet hours while schedules already exist. | Logic tests passed; phone not run |
| Focus linked to task | That task's reminders pause for running focus; pause/break/end releases suppression; timer recovers after reopening. | Logic/browser passed; phone not run |
| Partner completes/edits while other phone sleeps or is offline | Define measured connected propagation and bounded offline behavior before enabling shared background alerts. Test revocation and reconnect. | Blocked on database implementation |
| Daily missed days, pause, travel and DST | One dated occurrence, preserved history and agreed household timezone; no duplicate day or silent completion. | Pending Daily implementation |

An acceptable trial has **zero stale reminders after locally confirmed cancellation and zero duplicated task occurrences** in the scripted cases. Notification delay must be reported with its distribution and worst case, not a single successful screenshot. If ten-minute background persistence is too weak for the user's actual need, revisit native alarm capabilities and product scope before adding more screens.

## Reproduce local checks

Use the committed lockfile with `npm ci`, then `npm test`, `npm run typecheck`, `npm run build`, and `npx cap sync android`. Node 22+ and Java 21 are the chosen Android CI baseline; full native compilation also needs Android tooling. `npm run dev` starts local development. The app is statically exported; `next start` is not the production hosting workflow.

The build needs the existing public Supabase URL/key configuration to construct clients. Keep secrets out of source and out of browser variables. CI uses a synthetic public-shaped configuration for compilation only. Never substitute a different live project just to make an audit pass.

Root `AGENTS.md` and `CLAUDE.md` were generated by the upgraded Next.js development server, which instructs future agents to read its bundled version-specific documentation. The existing `.claude/settings.local.json` change and untracked `nul` file were preserved.
